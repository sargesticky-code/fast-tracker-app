# Phase 33 — One daily HKT match alias table

Owner direction: **remove duplicate Flashscore vs adviser Home/Away/name-alignment comparison from match Details**. The user does NOT wish to verify one match at a time. Treat source-linked names as **accepted for display until a concrete correction is reported directly in project chat**; preserve internal source identity tiers, never infer model accuracy.

- Dashboard: link **Daily aliases** to `/aliases`. Details has a single `Daily alias table` link.
- HKT date picker (±7 days), search, show all/source-linked/different-wording, copy visible tab-separated rows. One Flashscore fixture per table row with HKT kickoff, league, and original names from **Forebet**, **PrimaTips**, **Statarea**, **BetClan**, **SportyTrader**. Multiple source candidates remain visible; an absent linked source is `—`, not false zero or a fabricated alias.
- Backend: one SECURITY DEFINER read-only Postgres RPC for the requested HKT day; `EXECUTE` revoked from `PUBLIC/anon/authenticated`, accessible only to Edge service key. Edge exposes only bounded GET `daily-alias-matrix?date=YYYY-MM-DD`, ±7 days, read-only public source-name evidence, max 800 FS fixtures, 120s cache. No public writes.
- Data: Flashscore fixture anchor. Provider data from existing Forebet prediction and provisional sources, BetClan/SportyTrader verified and live provisional records, PrimaTips/Statarea existing candidate + source observation joins. Do not create new aliases from 30% provisional associations or treat no correction as scientific identity verification.
- No new collector, provider, HKJC connection, dedicated DB table, SQL cron/scheduler, or duplicate snapshot. **Scheduling** is a separate daily ChatGPT automation delivering a link and selected summary; the page resolves live data on demand, so scheduled content is automatically the newest stored data and uses no new DB capture.
- When a wrong match is reported: validate exact `FS:` fixture, date, oriented teams, source event id/URL; then update existing alias registry only with corrected source evidence. Quarantine conflicting mappings and regression-test before future collector snapshots.
- QA: CI + REST response of date and source counts, negative GET-date/POST, full public Railway deploy, browser page/mobile validation where possible. `SOURCE_LINKED` vs `PROVISIONAL` in table refers to recorded fixture identity, *not* forecast precision.
